# 配音：本机的 IndexTTS-2.5

官方仓库装在 `tools/index-tts`（自带 `.venv` 和 `checkpoints`，不进 Git）。所有脚本经根目录的 `tts.cmd` 调用，它负责用对解释器和环境变量。

## 东西都在哪

```
D:\Learn\
  朗读器.cmd               一键打开朗读器（双击；或把讲解的 HTML 拖到它上面）
  tts.cmd                  命令行入口：tts <命令> <参数>
  tools\tts\
    engine.py              模型的统一入口：路径、加载、音色、缓存、淡入淡出
    serve.py               常驻的配音服务
    app.py  app.html  app.ico   朗读器：配音服务加一个窗口
    synth.py  say.py       把配音嵌进成品；试听
    bench.py               测速
    voicelab\              做音色：流程在它的 README.md，工具是 harvest pick similar voice trial dialogue unpack（kif.py、pfs.py 读两种游戏包）
  voices\<音色名>\          一个音色一个文件夹，文件夹名就是音色名
    data\                  用户给的原件（音频、视频、台词文本），只读
    candidates\            从 data 里切出来的候选参考句
    trials\                每个候选试克隆的样句和分数表 scores.tsv
    voice.wav              定下来的参考句（有它，这个文件夹才算一个音色）
    voiceprint.npy         声纹，量克隆得像不像
    notes.md               这个音色的记录：素材来源、试过哪些、为什么选这一句
  out\                     运行时产生的，随时可删
    tts-cache\             合成过的句子
    subtitles\             朗读器提取出来的字幕
    app-data\              朗读器窗口的网页内核数据
```

`voices\` 和 `out\` 都不进 Git。音色只在本机自用，带这些音色的成品不要对外发布。

## 朗读器（平时就用这个）

双击根目录的 `朗读器.cmd`。它只开一个朗读器窗口，没有黑窗口：用的是 `pythonw`，日志写进 `out\朗读器.log`（每次启动重写），启动不了时弹一个框说原因。想在终端里盯着日志看，用 `tts app`。模型加载期间，顶栏是一条进度条加百分比（按上一次加载时各步用的时间估，记在 `out\tts-load.json`）；关掉朗读器窗口，整个程序立刻退出，显存也就放掉了。

窗口用的是 pywebview（系统自带的 WebView2 内核）：没有浏览器的账号、同步和扩展，标题栏涂成和界面一样的纸色。不要改回"Edge 应用模式加固定的资料目录"：Edge 会自动用 Windows 账号登录那份资料，把用户平时的扩展和同步数据都搬进去，深色类扩展还会改掉界面的颜色。没装 pywebview 时的退路也是 Edge，但每次用临时资料，并且关掉了登录、同步和扩展，标题栏是浏览器自己画的灰色。

- **选一讲。** 左边的侧边栏有两页。"文件"是 `D:\Learn\dist\` 的文件树：里面的 HTML 和文件夹都列出来，文件夹点一下展开、再点收起，可以一层层往下；点一个 HTML 就载入，侧边栏留在这一页，随时换另一个。新打包出来的几秒内自己出现；正在看的那一讲重新打包过，它那一行会多一个圆点，再点一下载入新的，并回到刚才看到的位置。"章节"是当前这一讲的章节，点一章从那里开始读。左上角的按钮收起、展开侧边栏。
- **别处的文件。** 侧边栏底部的"打开文件"从文件夹里选，也可以把 HTML 拖进窗口，或者直接拖到 `朗读器.cmd` 上。只认 `engine/build.mjs` 打出来的讲解。
- **画面。** 中间是画面区域，占掉侧边栏和字幕栏以外的全部地方，一直到窗口底边。讲解整幅放进去、居中，区域和画面的形状不一样时，多出来的地方是画面自己的底色，不是黑边。控制条固定在区域底部。只有窗口大小会改变画面大小。
- **字幕栏。** 右上角的按钮打开字幕栏：它接在画面区域右边，和它一样高，是同一张卡片的另一半。打开时窗口自己向右加宽，画面不缩小（画面两侧本来有空的话先用那块空）；关上时窗口收回去。窗口最大化、右边贴着屏幕边、或者是在浏览器里开的，窗口加宽不了，这时字幕栏从画面区域里占地方，画面等比缩小。
- **点哪读哪。** 在画面的进度条上点一个位置，在"章节"里点一章，或者在字幕栏里点一句，就从那里开始：先停在那一句的开头准备配音，声音到了接着往下读。
- **全屏。** 控制条右边有两个按钮："网页全屏"（W 键）让画面铺满朗读器的窗口，"全屏"（F 键）连窗口一起铺满整块屏幕。两种都只剩画面，没有进度条：控制条盖在画面底边，鼠标移到底边才出来，移开就收；鼠标停 2.5 秒不动也一起藏起来。空格、方向键照常用，Esc 退出。焦点不在画面里（刚点过侧边栏或字幕）时，这些键照样管用。
- **提取字幕。** 字幕栏上的"提取字幕"把字幕存到 `out\subtitles\`：`.srt` 是带时间的中文字幕，`.txt` 是每句一行的"编号、中文、译文"；同时把中文字幕复制到剪贴板。
- **选音色。** 顶栏的下拉框列出 `voices\` 下的音色，默认是咲来。出处相同的排在一起，默认音色所在的那一组排最前（现在是甜蜜女友的三个日语音色，然后是鸣潮的爱弥斯中文音色；守岸人、心月狐已于 2026-10-07 按用户要求移除）。换了之后，已经配好的句子按新音色重新来。
- **加一个音色。** `voices\<名字>\` 下有了 `voice.wav`，下拉框里就会出现这个名字，朗读器开着也会出现。同一个文件夹里再放一个 `voice.json`，写它说哪种语言和出自哪里，例如 `{"lang": "ja", "group": "甜蜜女友"}`：`group` 决定它在下拉框里和谁排在一起，`speed` 是这个音色的语速（模型的时长倍率，不写是 1，0.85 就是快一成半；只给换参考句也快不起来的音色用），`lang` 由 `GET /status` 报给朗读器。没有这个文件的音色排在最后。怎么从一堆音频做出 `voice.wav`，见下面"做一个音色"。

实测（示例片段，咲来音色）：启动到就绪约 35 到 40 秒；点第一句后等 3 到 4 秒开始读；之后按真实速度连续播放；跳到后面没配过的位置要等 3 到 6 秒，因为先得把正在合成的那一句做完。窗口被别的窗口盖住时照样往下读，最小化时会停。

### 读任意一段文字

不只是讲解的 HTML，随便一段文字也能读：

- **粘贴。** 在别处复制一段文字，回到朗读器按 Ctrl+V，立刻从这段的第一句开始读。把 `.txt`、`.md` 文件或者选中的文字拖进窗口也一样。已经在读别的文字时，新的一段接在列表后面，并且马上跳过去读它。
- **打字板。** 点侧边栏底部的"打字板"，或者粘贴过一次之后，画面下方有一个输入框：打字，回车就读，Shift+回车换行。正在读的时候再发一句，不打断，排在后面等轮到它。
- **自动分句。** 按句号、问号、感叹号、分号、省略号切，每一行算一段，段末停顿长一点（句间 0.25 秒，段间 0.6 秒）。一句太长（中日文超过 70 字，英文超过 220 个字符）就在靠近中间的逗号处再切一刀。Markdown 的记号、链接地址会先去掉。英文的句点只有后面是空格或引号才算句子结束，`Mr.`、`Dr.`、`e.g.`、人名首字母和小数点都不算。
- **语言逐句认。** 有假名的是日语，有汉字的是中文，其余是英语；整段以日语为主时（假名占中日文字的四分之一以上），只有汉字的句子也按日语读。认错了用底栏的"语言"整段改掉。
- **"流式"是整句整句地来。** 模型一次合成一整句，句子内部没法边合成边播。做法和讲解一样：第一句的声音一到就开始读，同时一句一句往前合成，最多取到播放位置之后 90 秒，所以只有开头等 1 到 3 秒。
- **点哪读哪。** 字幕栏里列出切好的句子，点一句就从那句读；底栏有上一句、下一句、进度条、语速，空格键暂停和继续，左右方向键换句。"换一段"清空，回到开始页。
- **情感。** 底栏的"情感"弹出八根推子：欢快、生气、悲伤、害怕、厌恶、低落、惊讶、平静，各 0 到 100，可以同时推几根。它们调的是**正在读的那一句**：松手之后这一句按新的情感重新合成、重新读，列表里这一句后面标上例如"欢快 70"。"全部句子都用这组"把整段都设成这样，"复位"回到不加情感（照参考句原本的语气）。数值交给模型的情感向量之前，用模型自带的折算过一遍（`normalize_emo_vec`）：各项先乘一个系数（惊讶乘 0.69、平静乘 0.56，压得最多），总和超过 0.8 时按比例缩回 0.8。所以单推一根时，欢快、生气、悲伤、害怕推过八九成就不再变强；几根一起推到很高时总量被压住，起作用的是它们之间的比例。剩下的份额（1 减去总和）留给参考句原本的语气。
- **日语没有文本归一化。** 粘贴的日语里有阿拉伯数字、单位、符号时可能读错，要写成读法。中文和英文没有这个问题。

情感只在读文字时用得上；讲解的 HTML 里每句的语气跟着音色的参考句走。接口上 `/speak` 和 `/cached` 都能带 `mood`（见 `serve.py` 开头），不带时和以前完全一样，以前的缓存照旧命中。

界面照着 Claude Desktop 的浅色做，改的时候守住这几条（都是用户逐条提过的）：

- **一张页面，只有一块卡片。** 页面是 `#FAF9F5`，连标题栏在内。侧边栏直接放在页面上，是一行行平的列表。画面和字幕是同一张圆角卡片的两半：左半是画面区域加底部的控制条，右半是字幕栏，中间一条细线。卡片只有一圈细线，底色就是页面的纸色，所以画面上面的标题行和下面的控制条是同一个颜色；用户 2026-10-09 一眼看出过白色的控制条和纸色的标题行"不是完全一样"，不要再把卡片涂成白的。不要再给其中哪一半另套一层卡片，那是框里套框。
- **界面上不放说明性的句子。** 用户 2026-10-09 的原话："UI 里还充斥着很多这种小字，比如在下面打字、回车就读这种很抽象的文字"。空着的列表就空着，或者只写"没有章节"这样几个字；不写"载入之后这里列出…""点一句就从那一句开始读"这类教人怎么用的话。界面上的字只有按钮名、文件名和状态。
- **部件之间不画线。** 侧边栏的页签、标题、右上角的按钮在同一行（同高、同基线）。字幕标题和列表之间没有分隔线，只有列表滚动起来时才出现一条细线。
- **阴影只给真正浮着的东西**：弹出菜单和提示条。按钮、列表行、章节标签都是平的，靠悬停和按下时的底色变化回应。给它们加投影会显得格格不入。
- **不用系统原生的下拉框。** `app.html` 里的 `menu()` 把 `<select>` 换成一个安静的触发按钮加自绘的弹出面板（圆角、细边、勾选标记、键盘可用），音色和播放速度都用它。
- **只用一种无衬线字体**，界面和讲解画面里的字都是，字距加宽到 0.03 到 0.06em。不用衬线体和等宽字体：在中文 Windows 上它们会落到宋体一类，屏幕上又细又锐利。
- **字体是 HarmonyOS Sans SC 配 Inter**，用户的要求是"选最接近苹方的"。苹方是苹果的授权字体，不能拿到 Windows 上用；HarmonyOS Sans SC 是免费字体里和它观感最接近的，Inter 管英文和数字，接近苹果的 SF。对比过的另外两套是 Noto Sans SC 和 MiSans：Noto 的 `≤` 是斜的、`×` 很宽，MiSans 字面偏紧偏重。Claude 自己用的 Anthropic Sans 是商业字体，只有拉丁字母，中文在 Claude 里也是退回系统字体。
- **字体怎么接进来的。** 文件在 `tools\tts\fonts\`（不进 Git，来源和许可见那里的 README），配音服务从 `/fonts/` 提供。`app.html` 的 `FONT_CSS` 把它们合成一个叫 `Learn Sans` 的字体：每个字重先写中文字体，再用同样的字重写一条 Inter 并限定在拉丁字符范围，两条的字重必须相同，否则浏览器不会用到 Inter。同一段规则也注入讲解的页面；画布不会因为写了字体名就去加载网络字体，所以注入后要用 `document.fonts.load` 逐个字重加载，再调 `film.redraw()` 重画。
- **讲解单独双击打开时**没有 `Learn Sans`，画面按字体栈往后找。HarmonyOS Sans SC 和 Inter 都已经按用户的要求装给了当前用户（见 `fonts\README.md`），所以在这台机器上单独打开和在朗读器里看是同一套字体。换一台没装这两个字体的机器，会退到 Noto Sans SC 或微软雅黑。要让成品在哪里都一样，得在打包时把用到的字裁成小字体嵌进去（环境里已有 fontTools），这一步还没做。
- **强调色只有陶土色**（`#D97757`），只用在播放按钮、进度和当前句的编号上。

讲解的 HTML 自带一套深色的页面外框，章节列表在画面左侧一栏。载入时由 `app.html` 里的 `EMBED` 样式去掉它的页眉页脚、章节栏和外框，让它的播放器占满整个框：画面区域在上、能伸能缩，控制条在下、改成上面这套浅色。画面怎么放进区域是成品自己的事（`engine/player.js` 的 `resize`：按 1920×1080 整幅缩放、居中，画不到的地方露出舞台的底色）。

版面全由样式表排，脚本不算尺寸：侧边栏定宽，字幕栏定宽（卡片太窄时它先让，让到 280 为止），剩下的都是画面区域（最窄 400，是控制条一行排得下的宽度）。2026-10-08 之前的版面由一个 `fit()` 函数算画面该多宽、片段放左边还是下面，估错行高时就有东西被切掉，现在整个删了。改版面时守住的还是那一条：**任何东西都不放到会被切掉的位置**。改完开真窗口把窗口大小从最小扫到最大，侧边栏、字幕栏各开各关，逐个量。

脚本只管一件和尺寸有关的事：打开字幕栏时让窗口向右加宽（`showList` 调 `app.py` 里 `Host.widen`，就是界面里的 `pywebview.api.widen`），加宽的量是字幕栏的宽度减去画面两侧现有的空；关上时把加的那些还回去。窗口加宽期间中间一栏的宽度先定住，所以画面只排一次、不会先缩再放。不能加宽时（最大化、全屏、贴着屏幕右边、在浏览器里开）`widen` 返回 0，版面照常排。

侧边栏的文件树来自 `GET /films`（`serve.py` 的 `films()`，从 `dist` 起逐层列出文件夹和 HTML），每 3 秒问一次；点一个文件走 `GET /film/<相对路径>`。这两个接口只接受朗读器自己的界面发来的请求，路径里带 `..`、盘符、反斜杠的一律不给。

两种全屏都是成品自己的状态（`html.full`，样式在 `engine/player.css`），这时控制条仍用讲解自己的深色；屏幕和画面形状不一样时，多出来的地方同样是画面的底色。朗读器看到这个标记，就把放讲解的框铺满整个窗口。"全屏"用的是浏览器的全屏接口；WebView2 只会把画面铺满窗口，窗口本身要宿主来放大，pywebview 没有管，由 `app.py` 的 `follow_full_screen` 补上（网页进全屏窗口就跟着铺满屏幕，退出时回到原来的大小和位置）。

## 只开配音服务

不想开窗口、想在浏览器里看讲解时：

```powershell
# 开一次，一直留着；用完按 Ctrl+C 关掉。常驻约 7GB 显存、10GB 系统提交内存
.\tts serve --voice 咲来
```

然后用浏览器打开 `http://127.0.0.1:8766/`，这就是朗读器的页面，把成品 HTML 拖进去。成品自己不连配音服务，单独打开只有画面和字幕。朗读器给成品配音时：

- **开头等一下。** 时钟停在第一句开头，画面右上角显示"正在准备配音…"，这一句的声音到了才往下走。服务刚启动时要加载模型和预热，约 40 秒；就绪之后等 1 到 3 秒。
- **之后不用再等。** 合成比朗读快一倍（每 1 秒音频用 0.5 秒），朗读器一边播一边往前取，最多取到播放位置之后 90 秒。从中间任意位置开始播也一样，先等那一句。
- **时间轴跟着声音走。** 没到的句子先按字数估算时长，声音一到就换成真实时长，后面的时刻和章节时间随之重排，播放位置不动。
- **合成过的句子不再合成。** 音频按"语言、朗读文本、音色、语速"（给了情感时再加上那八个数）的指纹存在 `out\tts-cache`，各集共用。改了稿重新打包再打开，只有改过的句子需要等。换音色等于全部重来。
- **服务中途断了也能看。** 没有声音，时长全按估算。

服务只在 `127.0.0.1:8766` 上监听，接口列在 `serve.py` 开头。换音色、写字幕文件、关服务这几个接口只接受朗读器自己的界面发来的请求。

## 其他用法

```powershell
# 试听：边合成边播放，或存成文件。--lang 说明这段文字是什么语言（zh、ja、en），不给就是中文
.\tts say "我们先从一个最简单的问题开始。" --play
.\tts say --file 稿子.txt --lang ja --out out\试听.wav --voice 某个音色

# 把配音嵌进成品。嵌入的声音由朗读器来放；成品单独打开仍然没有声音
# 解说词清单由 node engine/build.mjs 生成在成片的 build 目录里；合成完再打包一次
.\tts synth --narration lessons\某讲\film\build\narration.json --out-dir lessons\某讲\film\build\audio --voice 咲来
```

`narration.json` 是 `{"lang": "ja", "lines": [...]}`，每项 `{"key": "s1", "text": "字幕文本", "tts": "朗读文本"}`。合成时读的是 `tts`。现场配音时合成过的句子，`synth` 会直接从缓存里拿，不重新合成。嵌入的配音和稿子对不上（改过译文或换了语言）的句子，打包时会提示，播放时仍由配音服务现场合成。

要模型出声的地方都走 `engine.speak`。模型给的原始音频有四样毛病，它一样一样管，朗读器进入一句时也总是从这句音频的最开头播：

- **句首的气声。** 句子之间的"电流声加爆破声"主要是它。有的参考句（咲来、结灯的大半候选）会让模型在话前面先吐一口气：没有音高的"嘶"一声，130 到 330 毫秒，有时和说话一样响，从第一个采样就满幅冒出来，隔几十毫秒的静音才开口。爱弥斯、心月狐、守岸人几乎没有。它和参考句里有多少喘气声、参考句怎么开头结尾都对不上，试了才知道。`engine.breath` 把它切掉，只认最有把握的一种（一上来就有声音、140 毫秒以上、没有音高、重心不在齿音那么高、后面隔着静音）：咲来 44 句里切 41 句，没有这个毛病的三个音色近 500 句只切了一句（确实是一口一秒长的气）。し、ひ、ふ、つ 开头的日语句子核对过，声母都留着。
- **句尾被掐。** 模型的采样偏向早点收尾，有的句子最后一个字还没落下去就停了（真人录音句末从响到静要 150 毫秒上下，这些句子只有三四十毫秒），爱弥斯旧参考句四句里有一句。`engine.ending` 量得出来；被掐的句子用长度惩罚 2 再读一遍，哪一遍收得干净用哪一遍。**不要把长度惩罚 2 设成默认**：2026-10-05 这么做过半天，带气声的音色因此句句多吐一口气（咲来从六成多的句子有、较轻，变成每句都有、更响更长，句尾也多出气声），所以只在补读时用。把束宽降到 1 对句尾没有用。
- **贴边。** 剩下没切掉的短气声、补读了也没说完的字，音频一头是贴着边的。`engine.soften` 两头各加 12 毫秒的淡入淡出，贴着边的那一头拉长到 40、60 毫秒。说完之后的气声没有去切：它和轻声读的最后一个字在指标上分不开（试过，把句末的"果"切掉了）。
- **响度不一。** 克隆出来的音量跟着参考句走，各个音色能差 5 分贝，轻的那个听着像在说悄悄话。`engine.leveled` 按说话的部分量响度，每一句都调到 `engine.LOUDNESS`（-18 分贝，咲来本来的响度），不削顶。

查这类毛病，先把用户实际听的那批音频（`out\tts-cache`，按修改时间找）的开头结尾一格一格打印出来看，别先猜。改的是之后合成的句子；缓存里已有的不会自己变（2026-10-05 把当时缓存里带句首气声的 58 句就地切过一遍）。

`--voice` 给音色名（`voices\` 下的文件夹名），不给就用默认音色咲来；也可以直接给一个音频文件的路径。

带发音标注的文字（里面有 `<`、`|`、`>`）不要直接写在 `tts say` 的命令行上，cmd 会把它们当成重定向，改用 `--file`。

## 配音语言和译文

字幕是中文。配音读哪种语言跟着当前音色走：音色的 `voice.json` 里写着它说哪种语言，`GET /status` 把它报给朗读器，成品里有这门语言的朗读文本就读它。所以日语音色读日语译文，中文音色读字幕。成品里没有这门语言，或者音色没标语言时，用 `script.js` 里 `LESSON.dub` 写的那一种；成品单独打开（它自己不出声）和配音服务没开时的时长也按它估。换音色时如果语言变了，朗读器会丢掉已经取到的配音、让成品按新语言重排时间轴，播放位置留在同一句。

译文放在这一集目录下的 `dub.<语言>.json`，是一张"句子编号 → 译文"的表，目录里有几种语言，打包时就带几种。

译文是用来念的，用户看不到它。翻译时：

- **一句对一句。** 编号和字幕相同，不合并也不拆分，因为画面和时间轴都挂在句子上。
- **译成讲课的口吻。** 日语用です・ます体，像老师在讲解；英语用 3Blue1Brown 那种对着一个人说话的语气。不要书面语。
- **短。** 念出来的长度尽量贴近中文原句。日语天然长三成左右，可有可无的修饰就省掉。意思不增不减。
- **写成能直接念的字。** 日语没有文本归一化，数字、符号、公式一律写成读法：`七つ`、`エヌ`、`ログ エヌ`。英语的数字会自动展开，公式和缩写仍然要写成读法：`O of log N`。
- **术语用那门语言里通行的说法。** 堆是 `ヒープ` 和 `heap`，不要硬译。
- **读音有歧义的地方加标注。** 日语汉字：`<数|かず>`、`<根|ね>`。英语多音词：`<minute|M AY0 . N UW1 T>`。
- **译完通读一遍。** 前后句的指代和衔接在译文里要成立。

中文不需要译文，中文音色直接读字幕。写法和读法不同的句子，在 `script.js` 那一句的选项里加 `tts`，例如字幕 `O(log N)`，`tts` 写"大 O log N"；负数写"负一"；多音字写成 `<行|HANG2>`。字幕里 `$...$` 的公式没写 `tts` 时，按引擎自带的念法读（`V.spoken`），念得生硬，所以带公式的句子都写上 `tts`，例如 `$n_h = n_{h-1} + n_{h-2} + 1$` 写"n h 等于 n h 减一，加 n h 减二，再加一"。

## 做一个音色

用户给音频，助手来调，调好了朗读器里就能选。整条流程、目录的规矩、怎么判断、相似度和语速这把尺的刻度，都写在 `voicelab\README.md`，做音色之前先读它。这里只留最要紧的几条：

- **音频放哪。** `voices\<名字>\data\`，原样放着，只读。和讲解的 `data` 是同一条规矩。
- **调的是什么。** IndexTTS 是零样本克隆，没有可以训练的权重，像不像几乎只取决于拿哪一句当参考。所以流程是：从 `data` 切出候选（`tts harvest`，游戏语音包用 `tts pick`），存声纹并剔掉不是这个人的（`tts similar --save`），让每个候选读同一组测试句（`tts trial`），看相似度和语速选一句复制成 `voice.wav`，写 `notes.md`。
- **怎么进朗读器。** 有了 `voice.wav` 就自动出现在音色下拉框里。换掉已有音色的 `voice.wav` 之后要重开朗读器。
- **试克隆之前先关朗读器。** 显存只够开一份模型：一份常驻约 7GB，桌面自己还占着 5GB 上下。
- **最后一步是用户听。** 分数只量音色像不像、语速正不正常；自然不自然要靠耳朵，用户说不对就换一句。

## 本机配置的依据

2026-10-03 在 RTX 5080 16GB、Ryzen 9 9950X3D、Windows 11 上实测（`.\tts bench`，每段文本三次取中位数）。实时率是合成用时除以音频时长，小于 1 即比朗读快。

| 配置 | 实时率 | 显存峰值 | 说明 |
|---|---|---|---|
| bf16（默认） | 0.41 | 7.0 GB | 最省内存 |
| bf16，束宽 1 | 0.36 | 6.6 GB | 快 12%，上游默认束宽是 3，降低后稳定性未听评 |
| fp32 | 0.35 | 9.0 GB | 快 15%，加 `--fp32` |
| bf16 + torch.compile | 不可用 | — | 自带的 `ptxas` 不认这代显卡 |

精度定为 bf16：用户 2026-10-04 对比 bf16 和 fp32 的试听后认为几乎没有区别。

流式（60 个 token 一段）：首段约 3.5 到 4 秒出声，之后每一段都比该播放的时刻早 6 秒以上就绪。

时间的 80% 花在 GPT 自回归阶段，此时显卡利用率只有约 40%，一个 CPU 核心满载，瓶颈是逐步调度的开销而不是显卡算力。上游的 `accel` 引擎针对的正是这一段，但它依赖 flash-attn，官方没有 Windows 预编译包，需要 MSVC 和 CUDA Toolkit 现场编译；TensorRT 后端只支持 Linux 和 2.0 模型。

每个进程启动有固定开销：加载约 20 秒，第一句另需约 16 秒预热。

## 系统提交内存：加载模型时怎么不崩

Windows 下显存占用也计入系统的"提交内存"（物理内存加页面文件的总额度）。加载一次模型要多用约 9GB，加载完常驻约 7GB。本机内存 30.8GB。页面文件 2026-10-05 傍晚用户又调大了一次，现在初始 32GB、最大 48GB，提交上限 62.8GB，当时余量 43GB，平时够用，下面这套办法很少再触发。此前是初始 16GB、最大 32GB，上限 46.8GB，其他程序常常已经占了 37 到 40GB，余量不够。任务管理器里看到的"可用内存"是物理内存，和这个不是一回事。

余量不够时直接加载，模型一口气要好几个 GB，页面文件来不及扩，进程以 `0xC0000005` 退出，还可能连带其他程序出错（2026-10-03 连带过 Claude 桌面端和 WMI 服务）。

现在由 `engine.load` 自己处理（`engine.room`），不用再手动看余量、关程序：

- 余量不到 17GB 时，先一小块一小块地占住 17GB 提交额度。只占额度，不碰物理内存。慢慢要，页面文件就扩得出来。
- 额度占着不放，另起一个线程盯着余量：模型一要内存、余量低于 6GB，就还一块。等于把额度交到模型手里。留 6GB 是因为模型有时一口气要 3GB，来不及一块一块地还（只留 3GB 时，有一次余量掉到过 0.1GB）。
- 不能"占完一把全还回去再加载"：实测还回去之后一两秒内上限就缩回几个 GB，加载时又得现扩。
- 加载完打印一行账：多用了多少、期间余量最低多少、占住的额度剩多少没用上。

2026-10-04 实测了四次，加载前余量都只有 7.3 到 7.7GB，全部正常加载。最后一次（和朗读器一样在后台线程里加载）：上限从 49.1GB 顶到 59.4GB，加载多用 10.3GB，期间余量最低 5.2GB，上限没有回缩。

页面文件扩到最大也不够时，`engine.load` 报 `MemoryError` 而不是硬加载，这时才需要关程序。朗读器里遇到这种情况，顶栏显示"内存不够，模型没加载"（别的原因是"模型没加载起来"），原话在鼠标悬停的提示和 `out\朗读器.log` 里。界面上的话要短，用户明确说过加载失败不该写一长串。

2026-10-05 就遇到了：连着三次被拦下，启动时余量分别是 4.0、8.6、7.6GB。当时别的程序占着 44GB 提交内存（Claude 桌面端 45 个进程合计 17GB，QQ 2.1GB，微信 1.7GB，Edge 1.5GB），页面文件已经扩到 24.5GB，离 32GB 的最大值只差 7.5GB，凑不出 17GB。这种时候不要去放宽门槛硬加载：上限顶到头、别的程序一点余量都没有，正是 10 月 3 日连带崩溃的情形。关掉几个占得多的程序（腾出 10GB 上下）再开。用 `Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit'` 看余量，按程序名汇总 `Get-Process` 的 `PagedMemorySize64` 看谁占得多。

`engine.py` 里"加载 w2v-bert 前先归还显存缓存"是更早的缓解办法，留着。

## 重新部署时

- 依赖：在 `tools/index-tts` 下 `uv sync --extra webui --extra torch_compile --default-index https://mirrors.aliyun.com/pypi/simple`。
- PyTorch 的两个大包经代理下载很慢。可以从南京大学镜像 `https://mirror.nju.edu.cn/pytorch/whl/cu128/` 直连分段下载，对照 `uv.lock` 里的 SHA-256 校验后 `uv pip install --no-deps` 装入，再删掉对应 dist-info 里的 `direct_url.json`，`uv sync` 就认为环境已齐。
- 另装了两个不在 IndexTTS 依赖清单里的包，`uv sync` 之后要重装：`uv pip install --python tools/index-tts/.venv/Scripts/python.exe av pywebview`。PyAV 给 `tts harvest` 解码 AAC（本机没有 ffmpeg），pywebview 是朗读器的窗口。
- 模型：`modelscope download --model IndexTeam/IndexTTS-2.5 --local_dir checkpoints`；辅助模型首次运行时自动下载到 `checkpoints/hf_cache`。
