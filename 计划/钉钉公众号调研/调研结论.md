## 前期实测：公众号后台本地采集已跑通

后续已整理为独立模块 `core/wechat/`，不再依赖本调研目录。通过数据库中的公众号名称直接发现并按名称添加已实测，文章链接已改为备用入口；无需用户逐个提供。多公众号共用快照，运行状态、文章、事件和微信版本记录统一持久化至应用数据目录。设计与接口见 `core/wechat/README.md`，固定适配基线见 `core/wechat/compatibility.json`。当前实测版本为 Windows 微信 4.1.15.13，不将版本号误当成密钥。原研究脚本和下列历史结果保留用于复核。

用户最新要求是「继续仅做后台研究」。本轮没有操作微信界面、重新登录、注入代码、设置调试断点、修改代理或证书。当前版本为 Windows 微信 4.1.15.13。

首次定位时在公众号库中检查 102 张消息表、2,239 行，其中 2,231 行使用 Zstandard 解压，解压与目标 XML 解析失败均为 0。后续缓存目标表标识，每次仅解析该表。不会读取个人聊天消息库。

本次 WAL 文件头有效，但第一个残留帧的 salt 与当前日志头不匹配，是日志重置后保留的旧尾部，因此没有可合并的新提交帧。读取器校验 WAL 文件头、连续帧校验和与提交边界，只合并已提交页；发生校验错误会报错并保留已有文章，不能默默显示「没有新消息」。原库与 WAL 始终只读。快照在内存中合并，随后才交给 SQLite 查询。

### 为什么先前扫描失败、这次成功

只检查 salt 邻接的原始 32 字节候选没有成功；补做 PBKDF2-HMAC-SHA512 256,000 轮派生，36 个候选也未通过。随后依据 [Tencent SQLCipher 结构](https://github.com/Tencent/sqlcipher/blob/445e1dbe066ee917e4475b028f90ff37efb04541/src/crypto_impl.c)定位到了与目标库 salt 完全匹配的运行时 codec。直接读取其 key/hmac_key 仍不通过认证。

[wcdb-key-tool](https://github.com/TANGandXUE/wcdb-key-tool/blob/main/wcdb_key_tool_windows.py)提供了运行时片段经过重复 XOR 处理的线索，但它的固定掩码没有在本机读通。当前实现仅对已确认属于目标库的 99 字节 keyspec，根据已知的 salt 后缀恢复该片段的重复掩码，再以第一页 HMAC 判断候选是否真实有效。此次候选通过认证，并成功验证、解析了整份目标库快照。不是把「找到像密钥的字节」当成读取成功。

实现未直接运行第三方全库导出工具，第三方算法线索及 MIT 声明保存于 `THIRD_PARTY_NOTICES.txt`。这属于本机特定版本的验证，不能宣称所有微信版本通用。

### 研究原型入口

需要本机 Python 3.14 和 PowerShell 7，以及已登录、正在运行的普通微信。当前原型只适配一个本地登录账号、`biz_message_0.db`、本机已验证的 4.1.15.13 版本。

首次添加，用一篇文章识别账号并导入已有本地推送：

```powershell
& 'C:\Program Files\Python314\python.exe' 'D:\Innovation\计划\钉钉公众号调研\sync-wechat-public-account.py' --article-url 'https://mp.weixin.qq.com/s/4qwgIC-4Fk_6Se9NvKSXYQ'
```

后续同步无需再访问种子文章页面：

```powershell
& 'C:\Program Files\Python314\python.exe' 'D:\Innovation\计划\钉钉公众号调研\sync-wechat-public-account.py' --biz 'MzA3MDk5NDA0NA=='
```

状态保存在 `wechat-watch-3070994044.json`。首次导入数量与之后新发现数量分开记录，以 `biz:mid:idx` 去重，保存公开 URL 的四个字段，剔除授权参数。读取失败不会覆盖旧结果；本机找不到目标账号时返回 `account_not_in_local_cache`，不能当成「公众号没有文章」。缓存中新发现的旧文章也不能直接标成刚发布，发布时间独立保留。

`test-wechat-research.py` 的 4 组测试通过，包括多篇图文展开、Zstandard 解压、其他账号过滤、授权字段剔除、重复导入、增量去重、旧数据保留，以及由原生 SQLite 生成的 WAL 提交、未提交溢出、残留尾部与篡改拒绝。真实账号又完成两次重复读取验证。

这是一套可被定时调用的研究脚本，尚未接入应用业务代码或创建定时任务。

### 已加载网页与 HTTP Session 的补充结果

此前从 WeChatAppEx 已加载的数据中提取了 29 条该号的公开链接，保存为 `wechat-local-articles.json`。其中「胡金秋领衔！全明星校园行即将登陆浙大！」的标题与 URL 已配对。它没有出现在本次 79 篇本地推送结果中。两组公开链接去重后共 94 条，直接说明网页曾加载的文章和本地收到的推送并不完全重合；不能把任何一组说成该公众号全部文章。

内存中也找到原生文章请求所需的 key、uin、pass_ticket 等参数；只在本机用于请求 `mp.weixin.qq.com`。使用这些参数后，历史接口从 `no session` 变为 `ret=0, errmsg=ok`，但 `msg_count=0`、`can_msg_continue=0`、`home_page_list=[]`，没有实际列表。换参数和 cookie jar 仍为空。因此未把 HTTP 状态或业务 `ok` 算作列表采集成功，也没有证明所有公众号接口都被关闭。遇到验证页面未绕过验证码。

### 对产品方案的结论

可以保留「粘贴一篇文章添加公众号」入口。账号 ID 的识别与定时发现新文分两步实现；本次已证明本地推送读取可以作为后一步的数据源，因此不必依赖微信读书，也不需要目标公众号管理员权限。

要依赖这条路线，用户需在普通微信中关注目标公众号，并让客户端收到、同步其推送。只提供文章链接，不能保证本机已有该号的数据。客户端离线、尚未同步、仅主页展示而未收到的文章、未群发内容，以及微信升级后的结构变更，都可能影响覆盖。

已经验证的是现有数据读取及重复同步；还没有观察到一次新的真实目标推送进入数据库再被脚本发现的全过程。正式接入前仍需验收新推送延迟、离线补齐、重启后恢复、版本变化和更多账号/分片数据库。当前结果足以支持继续做独立本地模块原型，不能标成长期稳定的全量订阅服务。

## 原帖逐图复核后的路径修正

### 本地授权存储检查

用户明确要求本地查找后，已只读检查注册表、千问办公账号文件和连接器数据库，并在本机解密核对元数据；没有输出令牌或把明文凭证写入项目。可复现脚本为 `inspect-local-auth.ps1`，只输出身份范围、有效期与凭证存在标记。

- `HKCU\\Software\\DwsCli\\keychain\\dws-cli` 有 3 条受 DPAPI 保护的凭证记录，分别对应身份槽、组织镜像、旧格式镜像。它们属于「我的AI团队」，认证来源均为 `mcp`，包含访问令牌和刷新令牌；未发现第二个浙江大学身份。
- `%APPDATA%\\QwenWorkCN\\auth.dat` 与 `auth-v2.dat` 是千问办公自身的登录态，用 Electron safeStorage 加密。当前记录的组织 ID、团队 ID、组织名为空，不能当成浙江大学的钉钉授权。
- `%APPDATA%\\QwenWorkCN\\data\\agents.db` 中，钉钉相关设置只有开关和允许本地 profile 的标记；两张 MCP OAuth 表都没有钉钉/DWS 的凭证记录。
- `%USERPROFILE%\\.qwenworkcn\\mcp-adaptor.config` 确有 token，但其目标是 `127.0.0.1` 的千问本地工具代理。客户端源码确认它由代理生成，不能当成钉钉服务端令牌。
- 当前客户端 `DwsAccessTokenService` 将托管令牌保存在内存 lease 中，按组织身份从服务端请求，身份切换时会清除缓存；这部分实现没有将 lease 落盘。本次没有读取进程内存，也不能用落盘文件检查排除曾经存在的内存缓存。

因此，“Windows 导出命令不支持”不妨碍读取本机已有授权，这一步已验证可行；但在检查到的本地持久化存储中，没有找到可替代当前个人团队授权的浙江大学钉钉凭证。

### 独立于千问办公的目标

官方 `dws` 是 Apache-2.0 开源 CLI，可以作为独立组件包装；已有本机登录态能由独立可执行文件读取。源码包含直接向钉钉 OAuth/MCP 端点续期的逻辑，Windows 凭证存于 DPAPI 保护的 `HKCU\\Software\\DwsCli\\keychain`，无需将令牌交给模型或明文写入项目。

但“程序独立”“原有登录态能用”“重新登录和续期不再依赖千问”“能读学校内部群”是不同验收项。目前只验证了独立程序使用个人团队现有登录态。尚未完成退出千问全部后台进程后的对照测试，也未完成到期续期测试。电脑操控曾被用户按 Esc 停止，随后停止了所有原生桌面输入。

后续应先验证学校组织下的千问托管连接器能否读取指定内部群，再确定是否有当前版本支持的授权迁移与独立续期方式。现阶段不应把仅能读取工作通知的适配器当作已完成的内部群模块。

## 个人团队授权后的成功验证

用户完成新一轮授权后，千问办公内置 CLI 与独立官方 CLI 的 `auth status` 均显示 `authenticated: true`、`token_valid: true`、`refresh_token_valid: true`，当前组织名称为「我的AI团队」。

使用独立官方 CLI `v1.0.63` 搜索「浙大」，成功返回一个名为「工作通知:浙江大学」的会话。随后按返回的会话 ID 请求最新 1 条消息，成功读取智云课堂在 2026 年 10 月 8 日 13:20:07 发出的上课提醒。测试未发送任何消息。

响应 `success: true`，消息数为 1，`hasMore: true`、`complete: false`；本次有意限制为单条，未遍历历史记录。这里不保存账号、会话或消息 ID、课程名称和完整消息正文。

实测结论是「个人团队授权至少能读取这个已有的校园通知会话」，不能扩大解释成所有浙大组织资源、所有课程群或加密消息均可读。访问令牌与刷新令牌当前有效，也不等于已经验证长期自动续期。

此前 Windows `auth export` 不支持的结果仍成立，但同机、同用户的接入已经不依赖导出。项目可调用本目录的独立 CLI，通过现有登录态进行只读采集。下节记录的是完成这轮授权前的失败过程。

原帖后续回复也限定了经验的可靠性。[作者在第 15 楼](https://linux.do/t/topic/2757670/15)说明这种授权能力少于组织 CLI；[第 17 楼](https://linux.do/t/topic/2757670/17)说明自己未找到好的保活方式，其公司加密消息 AI 看不到。不能把首帖中的「完全接管」当成当前账号的能力保证。

## 钉钉的能力与授权

[Linux.do 原帖](https://linux.do/t/topic/2757670)发表于 2026 年 8 月，作者称千问办公注入的授权可导出到独立 CLI。这个经验不能直接作为当前版本和浙大组织的可用性保证。[千问办公当前连接器文档](https://qwenwork.cn/docs/features/connectors)明确写明，实际能力取决于企业开通范围和授权。

本目录已从[千问办公官网](https://qwenwork.cn/)下载 Windows 安装包 `qwenworkcn-setup-x64.exe`，大小 303737680 字节。Windows 验证其签名为 Valid，签名主体为 DingTalk Technology Co., Ltd.。只做了解包和 CLI 探测，没有完成桌面安装、登录或连接器授权。

千问办公公开客户端代码包含组织托管授权、个人授权和连接失效处理。把二进制复制出来并不自动继承千问办公授权；导出一次凭证也不证明可长期刷新。标准 CLI 的登录流程可能仍需要组织管理员开通。无需机器人与无需组织授权是两项不同条件。

`dingtalk-read.ps1` 是下一轮测试用的只读入口，提供状态、按名称搜索群、读取指定群三个动作。状态分支已实跑，授权后的两个分支尚未验收。

### 首次连接与本地网页 Session

后续用户要求尝试读取占用中的 Cookie 后，已成功越过文件共享锁这一障碍。当前进程不是管理员，未使用卷影复制；通过微信网页辅助进程已持有的目标文件句柄建立只读映射，复制两份 Cookie 数据库。只匹配已知 multitab/webview 的 Cookies 文件，没有终止微信、注入代码或修改其文件指针。副本的 SQLite `quick_check` 均为 `ok`。

multitab 副本含有 `mp.weixin.qq.com` 的公众号网页 Cookie，其中根路径有 `wap_sid2`、`appmsg_token`、`pass_ticket`、`wxuin`、`wxtokenkey`、`devicetype`、`version`、`lang`、`rewardsn`。webview 副本没有匹配的微信公众号域名 Cookie。仅在本机内存解密所需域名及路径，未输出凭证值。关键 Cookie 的更新时间约为北京时间 2026 年 10 月 9 日 03:12，不能仅凭存在就判断当前有效。

带 Cookie 与 appmsg_token 请求「浙大体育与艺术」的历史列表，HTTP 200 但业务返回 `ret=-3, errmsg=no session`。增加本机微信实际使用的 User-Agent 后缀、uin/pass_ticket 请求参数后仍然是 `no session`。没有拿到文章列表。结果证明本地读取可行，但该次复用未获得服务端认可；原因可能涉及会话时效或所需上下文，未验证前不归因于其中某一项。

复现工具为 `snapshot-wechat-cookies.ps1` 和 `probe-wechat-session.ps1`。副本只落在当前用户 LocalAppData 的私有测试目录，未放进项目。测试后按精确路径删除两份临时副本的操作被自动审批策略拦截，仅返回「被策略阻止」；未改用其他方式重试删除，副本保留于 `%LOCALAPPDATA%\\CampusAgent\\wechat-session-probe\\d82680b64e03466ca262acb0988846f9`。下文文件占用记录是普通读取失败阶段的事实，不再是当前阻塞点。

用户提出首次通过网页、扫码或微信快捷登录完成连接。交互层可以这样设计，但官方网站应用 OAuth 与公众号历史页 Session 不能互换。

[微信官方的网站应用授权文档](https://developers.weixin.qq.com/doc/oplatform/developers/dev/auth/web.html)明确支持微信扫码和快捷登录。快捷登录复用已登录且未锁定的桌面微信，由用户在客户端确认。接入方需要审核通过的网站应用、AppID/AppSecret 和回调配置。文档列出的授权关系接口是换取令牌、续期、验证令牌和获取用户基本信息，未提供读取个人关注公众号列表或公众号推送消息的权限。登录凭证不能直接作为 `profile_ext/getmsg` 的网页 Session。

最初检查时，本机微信 4.1.15.13 的内置浏览器数据位于 `%APPDATA%\\Tencent\\xwechat\\radium\\web`。找到 `profiles/multitab_<账号标识>/Network/Cookies`（69632 字节）与 `profiles/webview_<账号标识>/Network/Cookies`（28672 字节），以及 Chromium Local State 加密配置。普通 SQLite/文件只读打开返回 `EBUSY`，当时没有看到 Cookie 内容。后续已通过只读句柄映射解决占用，见本节前文；这些初始失败不再是当前阻塞。

用户确认没有打开微信网页窗口，只有微信主程序。进一步检查发现 11 个 WeChatAppEx 后台进程、0 个主窗口，Cookie 库仍无法只读打开。因此不能把文件占用归因于用户打开网页，关闭可见网页也不是已证明有效的解决办法。

用户描述的“浏览器先提示允许识别本地微信，再切换快捷登录”与官方文档一致；文档明确说明 Chrome 142 及以上会提示本地网络访问权限。该权限允许授权页面与本机微信进行登录交互，不会把公众号网页 Cookie 或文章列表读取权限赋予第三方网站。

后续已完成目标域名 Cookie 与原生请求参数的只读复用测试。历史接口仍未返回实际文章列表，详见文首最新实测；产品研究已转向成功读通的本地公众号推送库。本次没有强制停止微信或修改浏览器保护设置。

普通微信客户端是另一条独立路线。客户端收到公众号群发后，消息数据本身包含标题、原文链接和多篇图文条目；已有[本地数据库转 RSS 的实现说明](https://osnsyc.top/posts/wechat-db-to-rss/)。该文章基于旧版微信 4.0，本次又在本机 4.1.15.13 上独立验证了目标公众号读取，详见文首。它需要用户在微信中关注目标号并让客户端接收消息，不能承诺任意公众号全部历史、未群发文章或离线期间的完整补齐。

旧教程也需要逐项核查。[wechat-article-exporter 的停更说明](https://github.com/wechat-article/wechat-article-exporter/issues/200)于 2026 年 7 月 30 日称其依赖的上游核心接口关闭，残留 Credential 路线需手工操作且未接入主流程。因此不把旧公众号后台方案描述成今天开箱即用。`sjzar/chatlog` 当前仓库只保留移除代码的说明，也不能直接当成可安装依赖。

另核对 `Bben-dot/WeChatOArss` 的实际源码：扫码登录为演示 mock，部分搜索失败返回模拟公众号，文章获取依赖第三方站点。其 README 中的功能列表不能作为真实采集可用性的证据，未采用该项目。

## 接到校园智能体的实施顺序

### 2026-10-09：微信读书路线与反爬强度复核

**判断：连接器体验可改善，技术接入门槛中等；长期低频运行仍有明显风控与覆盖风险。** 这是工程判断，没有官方“反爬等级”或公开通用配额。少量公众号只取链接值得试验，高频、大批量与严格时效不能直接承诺。

#### 当前可用方法的证据

- WeRSS 的 [2026-09-04 提交](https://github.com/rachelos/we-mp-rss/commit/c0dc66e9aba002353bd1c578a96ef30865277dea)明确恢复 `/web/mp/articles` 作为主采集路径，按返回分组分页补抓；失败时才回退 `/api/mp/cover`。其 [weread-mp 文档](https://github.com/rachelos/we-mp-rss/blob/main/docs/weread-mp.md)仍写列表已废弃，是未同步的旧说明，不能单独据此判死接口。
- [当前公众号采集实现](https://github.com/rachelos/we-mp-rss/blob/main/core/wx/model/weread_mp.py)使用 Cookie 和普通 HTTP 请求；所检查路径没有要求像电子书章节采集那样处理正文解密。此结论仅针对公众号路径，不能概括微信读书所有接口。
- [扫码实现](https://github.com/rachelos/we-mp-rss/blob/main/driver/weread_qr.py)已有获取登录二维码、等待手机确认、校验会话和 `/web/login/renewal` 续期逻辑。因此可以做“连接微信读书”入口；没有必要要求用户手工复制 Cookie，更不需要电脑微信数据库密钥。续期失败仍可能需要重新扫码，不是永久授权。
- 公众号标识可映射为 `MP_WXS_<数字ID>`。现有「浙大体育与艺术」对应 `MP_WXS_3070994044`，无需再次提供文章才能知道它的标识。新增账号可以利用微信读书书架中可列出的公众号，或用文章链接识别 ID；不能把微信读书书架当成微信全部关注列表。
- 原文链接由列表返回的 `originalId` 或 `reviewId` 还原；[2026-09-23 的修复](https://github.com/rachelos/we-mp-rss/commit/c480451b87dd3d3556ffa7910eda231b3339751e)说明 token 内的 `~` 需要还原成 `_`。公众号 ID 能生成查询入口，但仍不能凭空推导尚未返回的未来文章 token。

#### 风控实际影响

| 层面 | 证据与判断 |
|---|---|
| 登录 | 需要微信读书自己的网页登录态。扫码及自动续期已有实现，不能与普通微信 OAuth 基本身份授权互换。 |
| 请求认证 | 有效 Cookie 可以支持公众号列表请求；不同接口/会话上下文可能返回 HTTP 401/403 或业务错误，不能只看 HTTP 200。 |
| 频率限制 | [WeWe RSS README](https://github.com/cooderl/wewe-rss)明确提示频繁添加会触发限制，并有失效和受限状态。其节流设置是项目策略，不是平台许可的请求额度。 |
| 恢复 | [Wechat2RSS 使用指南](https://wechat2rss.xlab.app/deploy/guide)记录重新登录、手机端授权或验证等恢复方式；恢复时长不固定。 |
| 完整性 | `cover` 只能作为单篇兜底，不能冒充完整列表。该实现还可能把采集时刻写作兜底记录的时间，接入时应独立保存发布时间与发现时间。 |
| 更新时效 | [Wechat2RSS FAQ](https://wechat2rss.xlab.app/deploy/qa)给出的检查/延迟是小时尺度，并限制初始采集范围。这是该产品取舍，不是微信读书官方硬上限，但说明不能默认分钟级稳定。 |
| 长期维护 | WeWe RSS 已归档（最后 push 2026-03-20）；WeRSS 未归档（最后 push 2026-09-24）。后者较新的扫码、续期和分页实现更适合作为技术参考。 |

不能根据旧 issue 中的“像是永封”推断整个微信账号会永久封禁；现有证据首先支持微信读书采集能力受到限制。也不能保证所有限制都会在 24 小时后恢复。Cookie 生命周期、验证触发率、账号/IP因素的具体权重均没有本账号实测数据。

`MAX_REQUEST_PER_MINUTE=60` 不能当成微信读书允许每分钟采集 60 次：[WeWe RSS 的 app.module.ts](https://github.com/cooderl/wewe-rss/blob/main/apps/server/src/app.module.ts)将它用于自身 NestJS 服务的节流配置。项目的 `UPDATE_DELAY_TIME`、内容请求间隔等，同样只是项目设置。

原本两分钟一次的本地查询不访问微信读书服务器。若照搬到 20 个公众号，每天仅列表查询就约 `20 × 24 × 60 ÷ 2 = 14,400` 次，尚未计算分页、正文和登录。这不是本次允许量或封禁阈值，只是负载估算；远程来源需要独立的更新策略。

#### 建议的插件接入方式

保留当前已经验证的本地来源，为同一插件增加独立的 `weread` 来源，先实验验证，再决定默认值。连接流程为：打开官方微信读书登录页面 → 本人扫码/确认 → 本机加密保存该域名会话 → 验证目标公众号列表 → 低频更新标题与原文链接 → 现有正文模块按需读取。

直接请求 `weread.qq.com`，不依赖 WeWe RSS 默认第三方中转。只参考所需的认证和采集逻辑，不整套接入第三方应用。服务端提示验证时停止轮询并提示本人处理，不尝试自动绕过验证码或换身份继续请求。

第一轮验收建议选 3～5 个号，只请求文章列表，不批量抓正文；以每号约一小时的保守实验间隔开始。这不是安全保证，遇到限制就按服务端提示停止或延后。验收内容包括：多篇群发是否齐全、分页能否补齐两轮间的新文、72 小时会话续期情况、断网和退出宿主后的恢复、公众号原文链接是否准确，以及仅返回 cover 时能否明确报告不完整。不要通过压力测试寻找账号封控阈值。

两种来源的 ID 格式不同：现有本地来源是 `biz:mid:idx`，微信读书可能先得到短链 token。接入时应通过文章元数据建立同篇文章的别名映射，不能仅按标题去重，也不能切换来源后重复通知。

钉钉先做独立的只读适配层，进程调用 CLI，凭证留在本机；先按用户选择的群采集。账号或组织切换时隔离缓存，按会话和消息 ID 去重，保留服务端分页游标。达到采集上限或权限失败要显示“未取完整”，不能显示“没有新消息”。

公众号已用「浙大体育与艺术」验证本地读取及多篇图文展开，下一步验收新的真实推送、离线恢复和其他账号，再接入应用。采集器读取失败要报告断更，保留已有结果。文章链接统一去重后可交给现有正文解析，从内容提取报名截止、活动时间和办理事项，并保留原文入口。

微信读书应作为可选采集来源，不能作为添加公众号的前提。根据用户对独立性的要求，本轮已建立普通微信客户端的订阅号推送读取原型；WeRSS 的微信读书模式与付费 Wechat2RSS 可作其他候选。各条路线都需验证目标公众号的覆盖情况。体育抢票等时效要求很高的场景仍需测量真实推送延迟，并结合钉钉群和已接入的校园系统。

前期项目的 `ui/profile/catalog.mjs` 专门映射 ZJU Core 模块，测试要求模块真实存在。后续接入已将独立来源登记到 `LOCAL_PLUGINS` 并与 `CAMPUS_PLUGINS` 合并为 `APP_PLUGINS`，没有伪造 ZJU 模块。公众号插件的同步随应用生命周期运行，未创建外部定时任务；钉钉内部群仍未读通。
